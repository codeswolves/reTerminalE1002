## 1. 目标

### 1.1 要解决的问题

给**专利 / 论文**的 idea 一个专门的存放处。

这类想法现在只有两个去处，**两个都不合适**：

- 记进任务清单 —— 它还不是"要做的事"
- 记进备忘录 / 聊天记录 / 脑子里 —— 一个月后找不到，等于没记

"灵感胶囊"这个名字就是它的定位：**先封存，需要的时候才打开**。

### 1.2 与现有载体的关系：为什么必须新开一个

| 载体 | 它回答的问题 | 为什么装不下灵感 |
|---|---|---|
| `task_flows.json`（任务清单）| **这件事该怎么做完** | 任务有进度、估时、截止、象限；灵感**还没有形状** —— 它可能永远不落地。塞进去会污染三处口径：待办池数量、象限占比（见 §7.3）、完成率 |
| `week_plan.json`（周时间安排）| 这周装不装得下 | 灵感不占时间，进不了时间预算 |
| `projects.json`（项目 DAG）| 这件事的**依赖与阶段** | 项目是"已经在做的事"，灵感是"还没决定要不要做" |
| 临时任务（`temp`）| 已经发生的突发 | 那是**时间记录**，不是想法 |

**结论**：需要独立的数据文件 + 独立的页面。

### 1.3 不做什么（边界）

- **不做 AI 生成 / 补全灵感** —— 那是代你思考，会把"你的想法"变成"AI 的想法"
- **不做提醒推送** —— 理由见 §4.3
- **不做自动归档、自动删除** —— 删除权只在人手里
- **不在捕获时问优先级，也不做评分**（2026-09-29 收窄）—— 但**允许在卡片上事后标一个优先级**。

  原先这条写的是"不做评分 / 优先级"，理由是"一旦有分数，人就会为了分数去记录"。
  现在把范围收窄到**捕获那一刻**：真正的损失发生在捕获环节 —— 多一个决定就多一批想法
  根本不被记下来，而"没记下来"是**查不出来的**（§2.2）。卡片上的优先级是**事后**的判断，
  不影响捕获行为，所以不落在上面那条损失里。

  配套三条约束（缺一条它就退回成一个"分数"）：

  1. **不进捕获框**（§3.1）—— 捕获时只问一段话
  2. **不参与排序**（§5.3）—— 它只是个"值得先想"的标记，不改变任何顺序
  3. **不进任何统计口径**（§7.3）—— 不计入转出率、不进仪表盘、不进周自评的数字

  边界很清楚：**它让"哪几条更想先看"在扫列表时看得出来，但不让系统替你做判断** ——
  与 §4.3"系统呈现事实，人做判断"是同一条线
- **不做协作 / 分享 / 公网发布** —— 见 §7.4：**专利以"未公开"为新颖性的前提**
- **灵感不进象限占比分母** —— 理由同 `time-quadrant-design.md` §7.5

### 1.4 这个功能唯一的失败模式：灵感坟场

**必须先说清这件事，因为它决定了后面每一个设计选择。**

只记录不回顾，这个页面必然退化成一堆没人看的文字：它会显示"共 137 条灵感"，而你一条都不会再打开。
更糟的是 —— **记录动作本身会制造"我在积累"的错觉，掩盖"什么都没发生"的事实**。

所以本设计的三条主线：

| 环节 | 取向 | 对应章节 |
|---|---|---|
| **捕获** | 尽可能省事，几乎不要门槛 | §3 |
| **浮现** | 尽可能主动，但**不越权替你下结论** | §4 |
| **转出** | 有一条明确的路径：灵感 → 任务 → 开始占时间，才算真的活下来 | §5.4 |

§8 给出三个能判断"它到底有没有用"的信号。

## 2. 数据模型

### 2.1 `data/ideas.json`

```json
{
  "meta": { "updated": "2026/09/28" },
  "ideas": [
    {
      "id": "I007",
      "text": "开完规划会路上想到的：现在承载网流量预测还停在 ARIMA + 人工经验规则，是不是可以用图结构把拓扑关系吃进去",
      "title": "用图神经网络做承载网流量预测",
      "deliverable": ["论文", "专利"],
      "status": "设计中",
      "tags": ["承载网", "GNN", "流量预测"],
      "source": "P02 项目 9 月评审会上 X 提到的问题",
      "created": "2026/09/20",
      "notes": [
        { "date": "2026/09/22", "text": "查了下，18 年有篇 GNN 做骨干网预测的，但没考虑链路容量约束" },
        { "date": "2026/09/25", "text": "数据可以从 P02 的历史采集库拿，够训一个 baseline" }
      ],
      "linked_task": ""
    }
  ]
}
```

### 2.2 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 稳定标识 `I001` 起递增。页面与 API 都用它 —— **不用数组下标**：删一条就会让所有引用错位 |
| `text` | ✅ | 记下时的**原话**，不做整理 |
| `title` | ❌ | 一句话标题，用于列表扫读；没有就显示 `text` 的截断 |
| `deliverable` | ❌ | 可能产出什么，**多选**，取值域是 `meta.DELIVERABLE_ORDER` 的**子集** `{专利, 论文}`（§2.3）|
| `status` | ✅ | `种子` / `设计中` / `已转出` / `封存`，默认 `种子`（§2.4）|
| `priority` | ❌ | `high` / `medium` / `low`；**缺失 = 未评**（不是"中"）。只在卡片上设，不进捕获框、不参与排序（§2.7）|
| `tags` | ❌ | 自由文本，只服务检索（§2.6）|
| `source` | ❌ | 从哪来的（读到的论文 / 会议 / 讨论）。**专利要检索现有技术、论文要写相关工作**，这个线索过了两周就想不起来了 |
| `created` | ✅ | 记下那天 |
| `notes` | ❌ | 推进记录 `[{date, text}]` —— 不是"进度节点"，是"后来又想通了什么" |
| `linked_task` | ❌ | 已转出时指向任务清单里的任务号 |
| `why` | ❌ | **封存原因**（§2.5）|

**为什么必填只有 `text` 和 `status`**：捕获时的摩擦每多一个字段，就多一批想法根本没被记下来。
而**没记下来**是查不出来的 —— 你只会觉得"最近没什么想法"。这个损失不可观测，所以最贵。

### 2.3 `deliverable`：任务那套枚举的**子集**，不是新枚举

**灵感只记两个方向：`专利` 与 `论文`**（2026-09-28 收敛）。

这本来就是本页面存在的理由（§1.1）—— 它是个"专利 / 论文的 idea 存放处"。
`报告 / 文章 / 系统工具` 那几种更像是**任务产出的结果**，而不是"一个想法的走向"；
把它们摆在捕获框里，只多一次选择成本，换不来任何东西。

**实现上是子集，不是另立一套 `IDEA_KIND`：**

```python
# meta.py
DELIVERABLE_ORDER = ["论文", "标准", "专利", "报告", "系统/工具", "文章", "其他"]
# 灵感胶囊可选的那部分 —— 是**同一批字符串**的子集
IDEA_DELIVERABLE_ORDER = ["专利", "论文"]
```

两个理由：

1. 它回答的是同一个问题 —— 任务的 `deliverable` 是"这件事要产出什么"，灵感的是"这个想法可能产出什么"
2. **转出时零映射**（§5.4）：子集里的值就是任务那边的同一个字符串。
   另立一套就得再维护一张对照表，而两张表迟早对不上

**将来要加回一种？改 `IDEA_DELIVERABLE_ORDER` 一行即可** —— 不用动数据、不用动转出逻辑。

**边界（两条，合起来就是"读时不丢数据、写时守住取值域"）：**

| 时点 | 行为 |
|---|---|
| **写**（捕获 / 改字段）| 只接受子集内的值，子集外的**明确拒绝**（不静默丢弃）|
| **读**（渲染 / 分组）| 子集外的值**照常显示**并分到它自己那一组（动态分组天然支持，§5.3），配色走灰色兜底 —— 老数据、手改过的 JSON 都可能带别的值，**藏起来比显示出来更危险** |

**为什么是多选**：同一想法**既能申专利也能写论文**是常态（先发论文还是先申专利是**策略**问题，
不是这个想法的属性）。逼人选一个，等于在"该攒专利素材了"这类筛选场景下把它漏掉。

**为什么可留空**：刚冒出来的想法常常还看不出形态。**留空 = 未定**，是个合法状态，不该逼人现在决定。

### 2.4 状态机

```
  种子 ──→ 设计中 ──→ 已转出（＝ 转成任务，交棒给任务清单）
    ⇅                    （任一步都可 ──→ 封存，可逆）
```

| 流转 | 由谁决定 |
|---|---|
| `种子` ⇄ `设计中` | 人点（系统不自动升级）|
| `设计中` → `已转出` | **只能由「转成任务」进入**，不能手点（§5.4）|
| 任一步 → `封存` | 人点，且可逆（随时捞回来）|

| 状态 | 含义 | 进这个状态的信号 |
|---|---|---|
| `种子` | 刚记下，还没细想 | 默认 |
| `设计中` | 在想 / 在查文献 / 在找人聊 | **由人来点**，系统不自动升级 |
| `已转出` | 决定做，已转成任务 | **只能通过「转成任务」进入**（§5.4）|
| `封存` | 想过了，暂时不做 | 附一句 `why` |

**`已转出` 与 `linked_task` 必须同时成立**：把「已转出」定义成"转出成任务"，两者就永远不会矛盾 ——
否则会出现"标着已转出、却没有对应任务"的悬空状态，而那种状态在页面上看不出来。

**状态名取自实际工作语汇，不借比喻**（2026-09-28 调整）。原先叫 `孵化` / `已立项`，是通用灵感
管理里的说法；换成 `设计中` / `已转出` 是因为前者一眼落不到具体动作上、每次都要解释一遍。
`已转出` 还多一层好处：它**直接说出了发生了什么**，而不是让人以为"这个状态还归本页管"。

> 曾考虑把 `已转出` 叫「编制中」，放弃了：那会把状态从**交棒**变成**过程**（"在写文件"），
> 于是同一件事在灵感页与任务清单里各有一份状态、还可能对不上；而且"编制中"可以纯手点，
> 上面那条"状态与任务号同行成立"的不变量就破了。

### 2.5 为什么"封存"要留一句 `why`

因为**你迟早会再次想到同一个想法**。

那时最有用的信息不是"这个想法是什么"（你刚想到），而是"上次为什么把它放下了"：
是技术路线走不通？数据拿不到？还是当时没时间？—— **只有第一种值得你重新投入**。

不留这句，你会把同一个坑踩三次，每次都从头评估。

### 2.6 `tags` 为什么可以是自由文本

`time-quadrant-design.md` 里有一条强约定：**统计类字段必须用枚举，不能用自由文本**
（`BLOCKER_ORDER` 的理由是"自由文本统计不出'最常因为什么卡住'"）。这里不冲突：

| | 枚举的理由 | 灵感标签的实际情况 |
|---|---|---|
| 用途 | **统计**（占比、排名、反哺规则）| **检索**（"我那个跟 GNN 有关的想法呢"）|
| 取值可预见性 | 卡点就那么几类 | 灵感会出现在任何领域，**预先枚举不出来** |

硬要把标签做成枚举，结果就是捕获时**从固定列表里选一个不相干的** —— 那比不标更糟（污染检索）。

**边界**：`tags` 只用于筛选与检索，**不参与任何统计口径**，也不进仪表盘。

### 2.7 `priority`：一个**可选**的标记，不是分数

**缺失是合法状态**，显示为灰色的"未评"。这与 `deliverable` 的"留空 = 未定"是同一个取向
（§2.3）：刚冒出来的想法常常还看不出该不该先做，**不该逼人现在决定**。

**为什么不像任务那样给个默认值**（任务那边 `DEFAULT_PRIORITY = medium`）：任务的优先级在
**建任务那一刻**就已经由人想过一遍（表单里那个必选下拉）；而灵感是"一句话先存下来"，
此时替它填一个"中"**等于替人做了一个他没做过的判断** —— 与四象限页"象限留空 = 未归类、
不自动判定"是同一条理由。

因此读到一个认不出的值时也**不当成"中"**（那会把"我不知道它是什么"和"它就是中优先级"
混成一件事），只是按"未评"显示，并且不写回数据。

取值域**复用任务的** `PRIORITY_ORDER` / `PRIORITY_META`（含配色）：它回答的是同一个问题
（"这事该先做还是后做"），与 `deliverable` 复用 `DELIVERABLE_ORDER` 是同一种做法（§2.3）。
**写入时拒绝取值域外的值**（不静默丢弃）。

三条约束见 §1.3：不进捕获框、不参与排序、不进任何统计。

## 3. 捕获

### 3.1 零门槛：一段话就能存

页面首屏就是一个输入框，**回车即存**：

```
┌─────────────────────────────────────────────────────┐
│ 想到什么？                                        │
│ ┌─────────────────────────────────────────────────┐ │
│ │                                                 │ │
│ └─────────────────────────────────────────────────┘ │
│ 可能产出 [ 专利 ▾ ](可留空)  标签 [            ]    │
│                                    [ 存进胶囊 ⏎ ]   │
└─────────────────────────────────────────────────────┘
```

- **只要求一段话**（`text`）—— 不必先想标题、不必先归类
- 标题、标签、可能产出都可以留空，之后在卡片上补
- 存完输入框清空、光标回位，**不跳页、不弹确认**

### 3.2 标题是"要转出成任务时才必须想清的东西"

这是本设计里一个刻意的取舍：捕获时**不要求**标题。

理由：**"想个标题"是整理动作，不是记录动作**。
灵感来的时候往往是一句没头没尾的话（"是不是可以用图结构把拓扑吃进去"），
要求当场把它提炼成标题，就是把最该省事的那一步变成了负担。

列表里没有标题的条目就显示 `text` 的截断 —— **它看起来"未整理"，这是准确的**，不该被美化。

到了**转成任务**那一步，标题才变成必填（因为任务清单要显示它），
此时预填 `text` 的截断，人改一改就行。

### 3.3 二期：从其它页面随手记

一期的捕获入口只有本页面。但"灵感在别处冒出来"才是常态 ——
二期计划在四象限页 / 任务清单页的工具栏加一个 `💡` 按钮，弹一个只含一个输入框的小窗。

一期先不做，是因为要先确认这个页面本身有人用（§8）；否则只是多一个入口制造更多坟场。

## 4. 浮现（本设计的灵魂）

### 4.1 问题：记录 ≠ 用得上

灵感是**易逝**的，但也是**易沉**的。攒了 100 条之后，问题不再是"记不记得住"，
而是"**我怎么知道现在该看哪几条**"。

穷举式浏览（把 100 条铺在一屏）等于没有筛选。所以必须回答：
**哪几条应该在什么时候回到我眼前。**

### 4.2 三个机制

| 机制 | 做法 | 它回答什么 |
|---|---|---|
| **页内"久置"区** | 顶部列出 `设计中` 且超过 `N` 天（默认 21）没有新增 `notes` 的条目 | "哪些想法我放下了，但还没放下" |
| **周自评里带一句** | 写周自评时，在既有"机动构成"那一行下面再加一行：`本周 +3 条 · 设计中 7 条（2 条超过 3 周未动）` | 复盘时顺手看见 —— 与"把机动构成摆进周自评"是同一种做法 |
| **转出即闭环** | 转成任务后，它的时间投入自然进了四象限统计 | **灵感活下来的唯一硬证据**：它开始占时间了 |

### 4.3 为什么不做提醒推送 / 自动归档

**这两个都是"系统替你下结论"**，与这套系统一以贯之的取向冲突
（`time-quadrant-design.md` §1.4 专门列了"不做的事"；§2.1 里待安排区的判据也是从
"本周排满"改成"**任务做完了没有**"—— 同一类取舍）：

| 做法 | 为什么不做 |
|---|---|
| 推送提醒 | 打扰。而且通知只训练出"忽略通知"的习惯 |
| 自动把久置的条目归档 / 降权 | 等于替你判断"这个想法没价值了"。而**创意的价值和时间不成反比** —— 三年前的想法可能因为技术条件变了突然可行 |
| 给灵感打分 / 排序 | 一旦有分数，人就会为分数记录（§1.3）。所以卡片上那个优先级**不参与排序、不参与任何统计** —— 它只是一个标记，不是分数（§2.7）|

**正确的分界**：系统**呈现事实**（"3 条超过 3 周没动"），人**做判断**（要不要捞起来、还是封存）。
"久置"区只列出条目，**不带任何评价性措辞**，也不排序 —— 它和"机动构成"是同一类东西：
把数据摆出来，结论留给人。

### 4.4 一个刻意不做的事：不统计"灵感产出率"

不要做"本周灵感数"的曲线图。

因为**灵感数量不是产出**：逼自己每天记 3 条，只会得到 3 条垃圾。
一旦这个数字被展示，它就会变成 KPI —— 而这是最不该被 KPI 化的东西。
（可测的是**转出率**，见 §8，那是事后统计，不是当期目标。）

## 5. 页面设计

### 5.1 布局

```
┌ 灵感胶囊              任务清单 · 四象限 · 流程跟踪
│ 共 24 条 · 种子 6 · 设计中 11 · 已转出 5 · 封存 2
├
│  ┌ 快速捕获
│  │  想到什么？                              （回车即存）
│  │  可能产出 [▾]    标签 [        ]      [ 存进胶囊 ⏎ ]
│  └
├
│  ⏳ 久置 · 2 条                        （只列事实，不做判断）
```

### 5.2 快速捕获框

见 §3.1。**永远在页面最上方**，不折叠、不弹窗 —— 它承载的是"随手记"这个最高频动作。

### 5.3 视角、分组与筛选

**两套视角，由人切**（顶部「看：按状态 / 按产出」）：

| 视角 | 分组 | 回答的问题 |
|---|---|---|
| **按状态**（默认）| `种子` / `设计中` / `已转出` / `封存` | "我还有哪些没想过的？这件事走到哪了？" |
| **按产出** | 用到的每种 `deliverable` + `未定` | "**专利池**里有多少货？论文呢？" |

两套都得留，因为这是两个不同的问题，谁也替不了谁："今天要攒专利素材"问的是产出，
"我攒了几条还没看"问的是状态。只做一套的话，另一套只能靠筛选下拉去凑 ——
而那需要你先想起"该筛了"。

**按产出的分组是动态的**：用了哪几种就分哪几组（按 `DELIVERABLE_ORDER` 排），
没数据的类型不占版面 —— 与 `meta.collect_categories` 同一取向。
末尾追加一个 `未定`（`deliverable` 为空），因为"还没看出形态"是个真实的、不该被藏起来的状态。

**一条灵感可能同时出现在两个池里。** `deliverable` 是多选（§2.3），
所以"既能申专利又能写论文"的想法会在专利池与论文池里**各出现一次**。
不藏任何一边 —— 藏起来会让人以为那个方向没货；卡片上的角标（`专利` `论文`）
正好解释了它为什么在这里，组标题也会标出 `· N 条同时也在别的池`。

其余约定：

- 组内按 `created` 倒序（新的在前）
- **按状态**视角下 `已转出` 与 `封存` 默认收起（和四象限页"已完成任务默认收起"同一个理由：
  页面首先是"当前还在想的事"，历史一直占着位置会把它们挤下去）；
  **按产出**视角下**全部展开** —— 那个视角的用途就是一眼看全两个池
- **状态变更后，目标分组必须自动展开**（做 demo 时踩出来的）：
  把一条灵感切到 `封存`、或转成 `已转出`，它就从"展开的组"移进了"收起的组" ——
  不展开的话卡片**当场消失**，人只会以为操作没生效或自己点错了。
  这与四象限页反复提醒的"藏起来 = 任务凭空消失"是同一类毛病。
  **三处状态变更（点徽标切换 / 封存 / 转成任务）共用一个出口**（`revealGroup(g)`），
  各写一遍一定会漏掉其中一处（先漏的就是"点徽标切换"那条路）
- 分组的展开状态**只记用户显式动过的**，默认值放一张表 ——
  这样两套视角各有各的默认（按产出全展开、按状态收起两组），又不会互相污染
- 筛选：状态（页签）+ `deliverable` + `tags`，可叠加，两套视角下都生效。
  **按产出视角下要把同义的 `deliverable` 下拉收起来** —— 它已经成了分组维度，
  再摆一个只会让人以为它还有别的用处
- **久置区不受视角与筛选影响**（页面上明写这一句）。它的职责是"提醒哪些想法被搁下了"，
  一筛就看不见另一边搁下的了 —— 而那正是它要防的事
- **没有"按热度/价值排序"** —— 理由见 §4.3。卡片上的**优先级只是一个标记**：
  它不参与排序、不做筛选维度、不进任何统计，颜色只用来在扫列表时把"值得先想的几条"露出来（§2.7）

### 5.4 卡片与"转成任务"

卡片上就地可做的事：

| 操作 | 行为 |
|---|---|
| 点状态徽标 | 弹出可去的状态（`种子` ⇄ `设计中`、任一步 → `封存`）。**`已转出` 不给点**，只能由转出进入（§2.4）|
| **点优先级角标** | 就地设 `high` / `medium` / `low`，或清回"未评"。它不参与排序（§2.7）|
| 点 `deliverable` 角标 | 就地加 / 去。它是多选、而且只有两个值，不值得为它开弹窗 |
| 点 `tags` | 就地编辑 |
| 加推进记录 | 一行输入，回车即存（记 `date` + `text`）。**不改状态** —— 系统不自动升级状态（§2.4）|
| 封存 | 弹一句「为什么先放下？（可留空）」→ 存进 `why`（§2.5）|
| **转成任务** | 见下 |
| 解除关联 | 只在 `linked_task` 悬空时出现（§7.6）；**状态一起退回**，否则会造出"标着已转出、却没有任务" |
| 删除 | 带二次确认；**不可恢复**（与删除任务同一处理）。提示里明写"只是暂时不做就用封存" |

> **状态变更后目标分组必须自动展开**（§5.3），否则卡片会当场"消失" ——
> 切状态、封存、转成任务三处共用同一个出口 `revealGroup()`。
>
> **已转出组收起时，组标题也要报出关联失效的条数**：那条 ⚠ 在卡片里，卡片一收起就看不见了，
> 而"标着已转出、点进去什么都没有"正是 §7.6 要防的事。

**转成任务**（`已转出` 的唯一入口）：

1. 弹窗要求一个**任务名**，预填 `title` 或 `text` 的截断
2. 若 `deliverable` 选了多个，**让人选一个主产出**（这是任务的字段，单选）——
   默认取第一个，但必须由人确认：**"先发论文还是先申专利"是策略判断，系统不该替他定**
3. 创建任务时带过去的：`name`、`deliverable`（选中的那个）、
   **`text` 与 `source` 写进任务的"创建"节点备注**（保真 —— 灵感的原始表述不该丢），
   以及**已标过的 `priority`**
4. **不带**过去：象限（留空 = 未归类，之后在象限里归）、预估工时（留空 = 未估算）、
   分类（用默认值）—— 都遵守既有约定：不替人判断、未估算 ≠ 0

> 优先级**要**带过去：人在灵感上已经明确判断过一次，到任务那边悄悄变回"中"就是一次**无声的降级**。
> "不带过去"针对的是那些**还没到判断时候**的字段（象限、估时）—— 它们的"留空"本身就是正确的状态。
5. 灵感侧：`status = 已转出`、`linked_task = 新任务号`
6. **灵感原文不删** —— 想法会演化，原始表述有独立价值；任务的节点备注是副本

> 转出后的路径就交回既有系统了：任务进待安排池 → 拖进周表 → 占时间 → 进象限统计。
> **这才是灵感"活下来"的标志**，也是本页面与四象限之间唯一的硬连接。

### 5.5 移动端

单列、捕获框固定在顶部；`tags` / `notes` 折行展示。
沿用 `mobile-responsive.md` 的约定：**每个 flex 子项都要写 `min-width: 0`**（§5.4）。

## 6. REST API

**全部挂在 `/idea_api/` 前缀下，不是 `/api/`。** 这不是命名癖 ——
公网 nginx 只反代了 `location /api/`（`task-flow-public-deploy.md`），
放在 `/api/` 下等于**把专利想法暴露在一个无鉴权的公网端点上**。理由展开见 §7.4。

| 接口 | 方法 | 作用 |
|---|---|---|
| `/idea_api/list` | GET | 读取全部灵感（含计算字段，如"距上次推进多少天"）|
| `/idea_api/add` | POST | 新增一条：`{text, deliverable, tags}` → 服务端分配 `id` |
| `/idea_api/set_field` | POST | 改一个字段：`{id, key, value}`（`text`/`title`/`deliverable`/`tags`/`status`/`why`）|
| `/idea_api/add_note` | POST | 追加一条推进记录：`{id, text}` |
| `/idea_api/promote` | POST | **转成任务**：`{id, name, deliverable}` → 建任务并回写 `status`/`linked_task`（§5.4）|
| `/idea_api/unlink` | POST | 解除与任务的关联：`{id, status}` —— 状态一起退回（§7.6）|
| `/idea_api/delete` | POST | 删除：`{id}` |

**共 7 个**（`unlink` 是 §7.6 要求"解除关联"之后加的：没有它，悬空的那条就只能靠手改 JSON）。

`set_field` 只认一份**字段白名单**（`text` / `title` / `deliverable` / `tags` / `source` /
`status` / `priority` / `why`），且：

- `deliverable` 与 `priority` **写入时拒绝取值域外的值**（§2.3 / §2.7）
- `status` **不接受 `已转出`** —— 那个状态只能由 `promote` 进入（§2.4）
- `id` / `created` / `notes` / `linked_task` 不在白名单里：它们各有各的流转规则
  （`id` 服务端分配、`created` 不可变、`notes` 走 `add_note`、`linked_task` 与 `status`
  由 `promote` / `unlink` 成对修改）。**用白名单而不是黑名单** —— 黑名单漏一个就是
  一条静默的脏数据通道

约定沿用既有页面（`time-quadrant-design.md` §7.4）：

- 每个端点都是"**读整个 JSON → 改一个字段 → 整文件写回**"，所以**前端必须串行提交**
- 服务端读-改-写全程持 `threading.Lock()`（与 `week_plan.py` 的 `_FILE_LOCK` 同 pattern）
- 返回值统一 `{ok: bool, ...}`，失败带 `error`（给人看的一句话）
- 写 JSON 时 `ensure_ascii=False, indent=2`；**`allow_nan=False`**（写出 NaN 会让前端 `JSON.parse` 失败）

## 7. 已知坑与约定

### 7.1 转成任务要写两个文件，不可能是一个事务

`ideas.json` 与 `task_flows.json` 各有各的锁，**做不到跨文件事务**
（`/api/add_temp_task`、`/api/add_task` 都面对过同一个问题）。

**顺序必须是：先建任务 → 再回写灵感。**

- 反过来（先标 `已转出` 再建任务）：中途失败会留下"**灵感说已转出、任务却不存在**"——
  而灵感页看起来一切正常，**这种脏数据没人会发现**
- 这个顺序失败则留下"任务建好了、灵感还停在设计中"——
  **明面上的不一致**（灵感页显示设计中，但任务清单里已有同名任务），重试或手动关联即可

失败时明确回报"任务已创建（No.N），但灵感状态没回写成功"，
不能笼统说"失败"—— 否则人会重试，然后建出第二条重复任务。

### 7.2 `ideas.json` 必须是独立文件

不能塞进 `task_flows.json` 复用一套读写。理由在 §1.2 已列，这里补一条**技术上的**：

`read_tasks()` 会从节点进度推出 `finished` / `today` / `total_days` 等计算字段，
并据此参与**待办池、象限占比、完成率、仪表盘**四处统计。
灵感一旦混进这个数组，要么被这些统计算进去（污染口径），
要么到处加 `if not is_idea` 的例外（每个消费方都要记得加，迟早漏一处）。

### 7.3 灵感不进象限占比分母

`time-quadrant-design.md` §7.5 那条理由在这里同样成立，而且更强：

象限占比的分母是"**已估算总工时**"。灵感的 `estimate_h` 是空的（还没估、甚至还没决定做），
把它按 0 或按某个猜测值算进分母，会**系统性摊薄所有象限的比例** ——
A 类本身只有 1 小时多的量级，这个误差足以让结论反转。

**所以**：灵感的数据只在本页面内使用，**不参与任何跨页面的统计口径**。

### 7.4 ⚠️ 专利想法不能上公网（这条最不能让步）

公网部署的现状（`task-flow-public-deploy.md` §已知限制）：

> 公网 API **无鉴权**（个人博客，暂不设防）

而**专利以"未公开"为新颖性的前提** —— 想法一旦落在公网可访问的位置，
后续申请时"是否已公开"就成了一个真实的法律风险，而且**撤不回来**。

因此本功能有两条硬约束：

1. **API 放 `/idea_api/` 而不是 `/api/`**：nginx 只反代 `location /api/`，
   换个前缀就天然落在公网反代范围之外（**零成本**，且这条路径的命名本身就在提醒后来者）
2. **页面不纳入"平铺到博客站点根目录"的那套部署**：即不把 `ideas.html` 复制进公网静态目录

若将来确实需要在公网上看这个页面，**前置条件是先加鉴权**（Cloudflare Access 门禁或 nginx token 校验），
不能直接沿用任务页面那套"暂不设防"。

3. **四个任务页上的「💡 灵感胶囊」链接在公网会 404** —— 这是刻意的取舍，不是疏漏：
   链接是按 §9 第 5 项加的（本地要用），而页面不部署到公网（上面第 2 条）。
   要消除这个 404，正确做法是**先给页面加鉴权、再一并部署**，
   **不是**把链接删掉 —— 删掉等于本地也失去了入口。

### 7.5 时间戳按本地时区算

`created` / `notes[].date` 一律用 `date.today().strftime("%Y/%m/%d")`，
前端解析用**本地时区**构造 `Date`（不能用 `new Date("2026-09-28")` —— 那会被当成 UTC 午夜，
在西半球时区会落到前一天，与 `generate_quadrant.py` 里 `parseYmd` 那条注释同一个坑）。

"距上次推进多少天"这类计算字段由**读取时现算**，不落盘 ——
落盘的话隔天就过期了，而页面没有定时刷新。

### 7.6 `linked_task` 悬空要显式显示

灵感关联的任务被删除后（`/api/delete_task`），`linked_task` 会指向一个不存在的编号。

**不做自动解除、也不自动回滚状态** —— 那会静默改变历史。但要：

- 卡片上显式标出「⚠ 关联的任务已被删除」，并提供"重新关联 / 解除关联"
- 否则会出现"标着已转出、点进去什么都没有"，与 §7.1 要防的是同一类问题

## 8. 怎么判断这个页面有没有用

（对照 `time-quadrant-design.md` §8 里「每周机动额度」那条：一个功能要有**能证伪它的信号**
—— 那里是"长期用满 / 从未动用"，否则它只是增加了维护负担。）

| 信号 | 观察 | 结论 |
|---|---|---|
| **转出率**（`已转出` ÷ 总数）| 长期为 0 | 要么捕获太随意（记的都是不值得做的），要么这个页面根本没被回顾 —— 两者都说明当前形态失败了 |
| **设计中滞留** | `设计中` 条数与平均滞留天数持续上涨 | "设计中"退化成了垃圾桶。要么该封存（诚实承认不做），要么该转出 |
| **封存原因分布** | 高度集中在"没时间做" | **问题不在灵感，在时间预算** —— 直接指向四象限：这是一个"每天净可安排 35h 装不下"的证据，而不是"想法不够好" |

第三条尤其重要：它是本页面与四象限之间**唯一有意义的交叉验证**。
如果封存原因全是"没时间"，那么"攒更多灵感"不是解法，回到 `time-quadrant-design.md` §1.2 才是。

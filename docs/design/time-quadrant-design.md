# 时间管理四象限 — 设计文档

> 日期：2026-09-18
> 状态：设计中 🚧（仅设计，代码未实施）
> 范围：**第一期** = 任务分类 + 时间结构诊断（§1–§8）；**第二期** = 每日任务排程（§9），算法独立、依赖第一期数据
> 相关文件：`src/generators/generate_quadrant.py`（待新建）、`src/generators/meta.py`、`data/task_flows.json`

## 1. 目标

在现有任务清单（`data/task_flows.json`，43 个任务）之上，按**重要性 × 紧迫性**把任务归入四个象限，
并回答一个现有页面回答不了的问题：**我的时间分配，是否落在了合理结构上？**

### 1.1 四象限定义

| 象限 | 含义 | 俗称 | 典型场景 |
|------|------|------|----------|
| A | 重要且紧迫 | 马上做 | 论文 deadline 前一周、线上故障 |
| B | 重要但不紧迫 | 计划做 | 论文日常推进、能力建设、长期项目 |
| C | 紧迫但不重要 | 快速做 / 委托 | 临时会议、他人转来的琐事 |
| D | 不重要也不紧迫 | 看情况做 | 无信息量的刷屏、可删的待办 |

### 1.2 时间投入原则（本设计的核心约束）

| 象限 | 目标投入占比 | 每天目标（7h 基准） | 设计解读 |
|------|--------------|--------------------|----------|
| A | 20% – 25% | 1.40 – 1.75h | 救火有成本上限，超过即说明预防不足 |
| B | 65% – 80% | 4.55 – 5.60h | **主战场**，长期价值全部来自这里 |
| C | ≤ 15% | ≤ 1.05h | 原话是单值 15%，按"上限"处理 |
| D | 0% | 0h | 不专门安排时间 |

"每天目标"一列是本文档最有用的一次换算 —— **25% 是抽象的，"A 类每天别超过 1.75 小时"才是可执行的标准**。

这张表不是普通的配比建议，它表达的是一个强判断：**B 类必须吃掉三分之二以上的时间**。

A 类占比高**不是**"努力"的证据，而是 B 类投入不足的结果 —— 救火任务几乎都是拖出来的。
页面的诊断逻辑全部围绕这一点展开（见 §3.4）。

### 1.3 时间预算与机动时间

比例必须先有分母。工作安排原则：

```
每天毛可用时间             8.0h
  − 机动预留（应对突发）    1.0h   ← 不参与象限分配
  = 每天净可安排时间         7.0h   ← 四象限比例的分母
  × 每周安排天数 5 天
  = 每周净可安排时间        35.0h
```

三条约定：

| 约定 | 说明 |
|------|------|
| **分母是 7h，不是 8h** | 机动时间在分母之外。把它算进分母，等于预先给"未知"分配了确定的时间 |
| **机动时间只用于真突发** | 仅处理"计划外的、必须今天处理的"事。若某件事每周都在吃机动时间，它就不是突发 —— 它是一条早该进任务清单的 C 类（或已失控的 A 类） |
| **7h 是容量上限，不是必须填满的目标** | 排到 7h 意味着零额外余量，一旦有波动就会反过来侵占机动时间。这也是**帕金森定律**的直接要求（见 §1.6） |

机动时间的存在，本身就解释了 A 类目标为什么只有 20–25%：**它正是给突发留的缓冲**。
反过来，如果机动时间长期被常规任务挤占（等价于把分母偷偷放大到 8h），所有象限的占比会被系统性摊薄，
比例结论随之失效（见 §7.5）。

预算参数作为常量定义在 `meta.py`（遵守单一来源约定），页面可临时调整天数与机动时长，**不落盘**：

```python
DAY_HOURS = 8            # 每天毛可用时间
DAY_BUFFER_H = 1         # 每天机动预留（不参与象限分配）
DAY_PLAN_H = DAY_HOURS - DAY_BUFFER_H          # 每天净可安排 = 7
PLAN_DAYS_PER_WEEK = 5   # 每周安排天数（默认工作日）
WEEK_PLAN_H = DAY_PLAN_H * PLAN_DAYS_PER_WEEK  # 每周净可安排 = 35
```

### 1.4 不做的事

- **不做任务计时/打卡**：没有数据源，且维护成本高
- **不改动仪表盘**：`dashboard.html` 是墨水屏 800×480 的固定版式
- **不做甘特图/日历排班**：四象限只回答"结构是否合理"，不回答"具体几点做什么"

### 1.5 实施分期

本文档分两期，**第二期依赖第一期积累的数据**：

| 期 | 功能 | 本质 | 依赖 |
|----|------|------|------|
| 第一期 | 四象限分类 + 时间结构诊断 | **分类**：回答"我的时间结构对不对" | 只需 `quadrant` + `estimate_h` 两个字段 |
| 第二期 | 每日任务排程（§9） | **决策**：回答"今天具体做什么" | 需要第一期积累两周以上的估时与完成数据 |

分期不只是工作量问题，更是**数据依赖**：排程算法的配额来自象限比例，候选排序依赖历史推进记录。
第一期没跑起来之前，第二期没有可用的输入。

### 1.6 三条定律及其设计含义

下面三条定律是 §1.2、§1.3 与 §9 排程算法的理论依据。**它们不是背景知识 —— 每条都对应一个具体的设计决策**，
否则不会写进设计文档。

#### 伊利赫定律（Illich's Law）

> 人在工作一段时间后效率会下滑，越来越难以集中精力，可以适当休息 10–20 分钟。

**设计含义**：工作块必须有边界，且休息点应当**主动安排**（在疲劳点之前休息的效率最高）。

| 决策 | 位置 |
|------|------|
| 单块时长 ≤ 2h，不允许出现"连续 4 小时"这类排法 | §9.5(6) |
| `chunk_h` 上限 2h | §9.6 |
| 块间显式插入 10–20 分钟休息，休息**不计入任务估时** | §9.5(6) |

由此产生一个必须说清的**口径约定**：`estimate_h` 记录的是**净专注时间**，而 7h 预算不可能全是专注 ——
休息会自然发生。所以：

- **排到 7h 是偏乐观的**，实际可完成的专注工作量低于 7h
- 建议排程只用到约 **6h（85%）**，把休息空间留出来
- 但这**不改变占比的分母** —— 比例是结构指标，与"排得多满"无关（§3.3 口径说明）

#### 卡尔森定律（Carlson's Law）

> 持续做一项工作，比零星地做这项工作花费的时间更少。

**设计含义**：**碎片化有隐性成本** —— 每切换一次，就要付一次上下文重建的代价。

| 决策 | 位置 |
|------|------|
| 同日 **slot 数 ≤ 4–5 个**，不允许"每个任务都碰一点" | §9.5(6) |
| 同一任务的多个块**优先连排**（batching），而非分散到多天 | §9.5(6) |
| 校验层拒绝违反 `chunk_h` 的碎片化安排 | §9.5(5) |

这条定律也是 **C 类必须封顶**的第二个理由：C 类任务天然碎片化（临时会议、回复他人、他人转来的事），
它们不仅自己消耗时间，还会**打断 B 类的工作块** —— 实际成本高于其名义时长。
这正是 15% 上限要防的事。

#### 帕金森定律（Parkinson's Law）

> 只要还有时间，工作就会不断扩展，直到用完所有时间。

**设计含义**：**没有时间盒，任何任务都会膨胀**。整份设计以"配额"为核心，根源就在这里。

| 决策 | 位置 |
|------|------|
| `estimate_h` + `chunk_h` 就是**时间盒**，没有盒子任务会自我膨胀 | §2.1、§9.6 |
| **7h 是上限而非填充目标** —— 把预算调到 8h 不会换来更多产出，只会换来膨胀 | §1.3 |
| **C 类必须在 15% 封顶** —— 紧迫的事永远做不完，不设上限它会吃掉全部可用时间 | §1.2、§9.5 |
| **B 类同样必须设时间盒** | 见下 |

最后一条最容易被忽略：**B 类没有外部 deadline，因此最容易受帕金森定律侵蚀**。
论文可以永远改下去，能力建设可以永远"再准备一下"。
所以 B 类任务必须自设时间盒（`estimate_h` 就是那个盒子），否则 B 类的高配额会被**单个任务的无限膨胀**吞掉 ——
表面上 B 类占比达标，实际上只推进了一件事。

## 2. 数据模型

### 2.1 新增字段

在 `data/task_flows.json` 的任务对象上新增两个**可选**顶层字段：

```json
{
  "no": "37",
  "name": "BGP-LS-SPF优化写一个论文",
  "priority": "high",
  "category": "科研",
  "due": "2026/09/16",
  "quadrant": "A",
  "estimate_h": 12,
  "nodes": [ { "phase": "创建", "date": "2026/09/01", "progress": 40, "note": "" } ]
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `quadrant` | `"A"` / `"B"` / `"C"` / `"D"` | 所属象限。**未标记时不写该字段**（不写 `null`、不写空串），页面显示在"待归类"区 |
| `estimate_h` | 数字（小时） | **预估剩余工时**，允许小数。未填则不参与占比统计 |

两个字段都是"有意为之的显式标记"，因此：

- 读取时缺失 → **保持缺失，不自动补默认值**（避免把"没想过"伪装成"已判定"）
- 页面取消标记时用 `pop` 删除字段，与 `pinned` 的处理方式保持一致（`serve_task_flow.py` L293-316）
- `quadrant` 取值必须落在 `QUADRANT_ORDER` 内，非法值按"未标记"处理并告警（脏数据只影响这一个字段）

### 2.2 为什么不复用 `priority`

现有 `priority`（high/medium/low）是**单维**的，四象限是**二维**的，二者无法互相推导：

- 「论文投稿」= high + 不紧迫 → B
- 「明天要交的报销单」= low + 紧迫 → C

若硬把 `priority` 当重要性、把 `due` 当紧迫性，会得到一个"看起来能跑但经常判错"的结果。
**`priority` 保持不变，继续用于排序；`quadrant` 是独立维度。**

补充：现有数据中 `due` 字段只有 1 个任务填写（No.37），所以"用 `due` 自动判紧迫性"在数据层面也不成立。

### 2.3 为什么不存两个布尔字段

也可以存 `importance: bool` + `urgency: bool`，但本设计选择单字段 `quadrant`：

- 四象限的语义是**归类**，不是连续打分系统；存两个布尔会产生 `false/false` 这类需要额外解释的组合
- 页面核心交互是"把卡片拖到某个格子里"，天然产出单值
- 单字段便于校验（只回退一个字段），脏数据处理简单

### 2.4 建议象限（推导，不落盘）

未标记的任务，页面给出一枚**建议角标**（浅色、可一键采纳），规则如下：

| 条件 | 建议 |
|------|------|
| `priority == high` 且（`delayed` 或 `days_left <= 7`） | A |
| `priority == high` 且不紧迫 | B |
| `priority == medium` 且紧迫 | C |
| `priority == medium` 且不紧迫 | B |
| `priority == low` 且紧迫 | C |
| `priority == low` 且不紧迫 | D |

`delayed` / `days_left` 是 `read_tasks()` 已有的派生字段（`generate_task_flow.py` L177-181），无需新增计算。

**推导结果永不自动写盘。** 宁可让用户看到"待归类"的堆积，也不要悄悄替用户做判定 ——
自动归类一旦出错，会污染整个占比结论，而用户不会察觉。

### 2.5 象限判定的自我提问清单

面对一件新事情时，先对自己提这 7 个问题，再决定是否让它进入任务清单、以及归入哪个象限：

| # | 提问 | 判断维度 |
|---|------|----------|
| 1 | 这件事能给组织带来价值吗？ | 价值 · 组织 |
| 2 | 这件事能给我带来价值吗？ | 价值 · 个人（当下） |
| 3 | 这件事对我的职业规划重要吗？ | 价值 · 个人（长期） |
| 4 | 这件事对我重要吗？ | 价值 · 个人（主观综合） |
| 5 | 我是唯一可以做这件事的人吗？ | 可替代性 |
| 6 | 拒绝他会损害我们的关系吗？ | 拒绝成本 · 关系 |
| 7 | 拒绝他会造成不利的影响吗？ | 拒绝成本 · 风险 |

#### 两个维度

- **Q1–Q4 → 重要性**：四问任一为"是"，即视为有价值
- **Q5–Q7 → 不可推卸性**：它是紧迫性的主要来源之一（与时间压力并列）。
  一件事可能没有 deadline，但因为"只有我能做 + 拒绝会得罪人"，事实上就变得紧迫

#### 映射到象限

| 有价值 | 不可推卸 | 处理 |
|--------|----------|------|
| 是 | 是 | **A** 重要且紧迫 —— 马上做 |
| 是 | 否 | **B** 重要不紧迫 —— 计划做 |
| 否 | 是 | **C** 紧迫不重要 —— 快速做或委托 |
| 否 | 否 | **拒绝，不入清单** |

最后一行的处理方式是这张表的关键：**D 象限的正解是"在入口拒绝"，而不是"归入 D 象限"**。
一件已经被登记进任务清单的事，即使标成 D，也已经占用了认知空间。
理想状态下 D 象限应该始终是空的 —— §4.3 的 D 空态文案正是这个意思。

#### Q5–Q7 的第二个用途：决定 C 类怎么处置

C 类有 15% 上限，所以"接不接"之外还要决定"怎么接"：

| Q5（我是唯一能做的人） | Q6 / Q7（拒绝有成本） | 处置 |
|------------------------|----------------------|------|
| 否 | 否 | **委托或拒绝** —— 最该被拒掉的一类 |
| 否 | 是 | **委托**（人情留给自己，时间交给别人） |
| 是 | — | 只能自己做，但严格卡在 15% 内 |

这与 §8 的 `delegate`（C 类委托标记）扩展直接对应。

#### 判定顺序

先问 Q1–Q4、再问 Q5–Q7 是有意的：

- 价值问题是**主判据** —— 无价值时，Q5–Q7 只影响"怎么拒绝"，不影响"该不该做"
- **快速通道**：Q1–Q4 全否，且 Q6、Q7 也否 → 直接拒绝，不必继续分析

#### 落地方式

这套提问适合做成**"待归类"任务卡片上的自检入口**，而不是新建任务时的强制流程 ——
7 个问题每次都答会让人放弃使用。勾选后按上表推导建议象限，用户确认再落盘，
与 §2.4 的推导建议走同一条交互路径。

### 2.6 沟通与拒绝的实操准则

§2.5 解决"该不该接"，本节解决"接住了怎么不被拖住"，以及"怎么拒绝"。
这些准则面向**意外来访、电话、谈话**这类高频打断 ——
它们是 C 类的主要来源，也是机动时间（§1.3）最容易被无声吃掉的场景。

#### 控制沟通时长

| 场景 | 准则 | 设计含义 |
|------|------|----------|
| 意外来访 | 先明确是否需要较长的沟通时间 | 当场分类：是 30 秒的事，还是 1 小时的事 |
| 意外来访 · 不需要 | 事先说明能留给他多少时间 | **现场设时间盒** —— 反制帕金森定律（§1.6） |
| 意外来访 · 需要 | 视具体问题约一个更合适的时间 | 把它从"当下的打断"变成"清单里的一条" |
| 各种电话 | 明确谈话目的，控制通话时间或另约 | 没有目的的沟通应当直接终止 |
| 任何谈话 | 及时拉回偏离的主题 | 谈话是最容易无限扩张的活动 |
| 谈话结束前 | 复述要点，确认对方达成共识 | **产出校验**：没有共识的谈话是纯沉没成本 |

**核心动作只有一个：在被打断的当下，立刻给出一个明确时长**（"我有 15 分钟"）。
它同时完成三件事 —— 把无形的黑洞变成有时间盒的事件、让对方调整预期、也给自己留出退出的合法性。

注意沟通的时间粒度比任务更细：任务的 `chunk_h` 是小时级（§9.6），
而这里的承诺时长通常落在 10–30 分钟区间，**不能直接复用 `chunk_h`**。

#### 拒绝他人

| 准则 | 说明 |
|------|------|
| 合理拒绝他人的请求 | 拒绝是正常动作，不是失礼 |
| 参考问题清单自我提问，判断是否要拒绝 | 直接复用 §2.5 的 Q1–Q7 |
| 态度诚恳，立场坚定 | 诚恳保住关系（对应 Q6），坚定避免反复 |

**"立场坚定"这条比它看起来重要**：模糊的拒绝（"我看看""可能不行"）比明确的拒绝成本更高 ——
对方会反复来试，于是一件本该被拒掉的事变成了**长期的注意力滴漏**。
拒绝得不彻底，等于把它从一次性的 C 类升级成了持续消耗。

诚恳与坚定并不矛盾：**诚恳针对人，坚定针对事**。

#### 与软件功能的关系

这套准则是人的行为约定，**不进入实施清单**（§6）；
其中唯一与程序相关的"参考问题清单自我提问"，由 §2.5 的自检入口承担。

### 2.7 估时方法

`estimate_h` 是 §3 占比统计的分母，也是 §9 排程配额的输入 —— **估时质量直接决定整套结论是否可信**。

前提判断：系统对估时的要求**不是"准"，而是"诚实且可校准"**。
估得不准可以接受（下面的机制专门处理它），但"看起来精确的错误估时"会让整套诊断失效（同 §7.2 的口径原则）。

#### 三条关键原则

**1. 用外部视角，而不是内部视角**

不要问"这件事要多久"，要问"**我上次做类似的事，实际花了多久**"。

做内部视角估算时，脑中的场景全是"一切顺利"的执行路径，所以系统性低估 —— 这是规划谬误，
也是少数几个有稳定改善手段的认知偏差。代价是冷启动期没有历史数据，只能保守估计并逐步积累。

**2. buffer 放在系统层，不要藏进每个任务**

不要给每个任务的估时偷偷乘 1.3。理由不是"麻烦"，而是：
**藏在任务里的 buffer 会让估算偏差永远不可见**，你也就永远学不会估。
§1.6 已经定了正确做法 —— 估时保持裸值，余量留在系统层（排 6h 而非 7h）。

**3. 回填，然后算自己的偏差系数**

定期计算 `实际用时 / 估算用时` 的比值。若稳定在 1.4，说明你系统性低估 40%。

关键在于：**你不需要把估时估准，只需要知道自己的偏差方向和幅度**，然后直接乘上去。
这是唯一能让估算随时间变好的机制 —— 没有回填，估时永远停留在第一天的水平。

#### 四条操作建议

| 建议 | 理由 |
|------|------|
| **只估近期任务** | 估时有保质期。给三个月后的任务估时是假精度，且会让维护成本失控。远期任务留空 —— "未估算"本就是合法状态（§3.3） |
| **单任务 ≤ 1 天（7h），理想 2–4h** | 估时超过一天说明**任务根本没被拆开**。2–4h 的任务一天能完成 1–2 个，有完成感，估算误差也可控 |
| **只估你的净投入，不算等待** | "净 2h"的任务可能跨 5 天（等评审、等结果）。**等待不是你的时间投入**，算进去占比会彻底失真。但别漏掉协作与收尾 —— 收尾（整理、记录、提交）常占 10–20%，几乎所有人都会漏估 |
| **`estimate_h` 与 `chunk_h` 一起给** | `6h ÷ 2h = 3 个块 = 占用 3 个时段`。这个除法才是"这周装不装得下"的答案，单看总量看不出来 |

#### 元建议

**估时要快，30 秒内给一个数。** 估时的最大风险从来不是不准，而是**因为太麻烦而被放弃**。
它的真正价值是迫使你面对"这周装不装得下"这个事实判断，而不是做一次精确预测。

### 2.8 AI 估时路线

#### 2.8.1 结论：人估 + Agent 校准，而不是 Agent 独立估

估时误差分两类，两类的最佳解法不同：

| 误差类型 | 表现 | 谁更擅长 |
|----------|------|----------|
| **系统性偏差** | 总是低估 40%（方向一致、幅度稳定） | 只能靠数据发现 → **Agent** |
| **单次特异性** | 这次特别难 / 今天状态好 | 只有当事人当场知道 → **人** |

Agent 独立估时会整个丢掉第二类。更麻烦的是**你无法审查它的数字从哪来** ——
它给 4h 还是 8h，你没有依据判断对错，只能全盘接受或全盘推翻。
而"人估 × 系数修正"两者都保住了。

#### 2.8.2 现有日期字段能提供什么

`read_tasks()` 已经派生出 `total_days`（完成 = 完成日 − 创建日），所以"开始/结束时间"是现成的。
但它能承担的角色需要说清楚：

**可以做的（无需任何回填数据）：**

| 用途 | 做法 |
|------|------|
| **上界校验** | `estimate_h ≤ total_days × 7h` —— 每天净可安排最多 7h（§1.3），净投入不可能超过"跨度 × 7h"。违反即是录入错误，可直接提示 |
| **相对量级排序** | 历时 30 天的任务与 2 天的任务，投入量级必然不同 |
| **异常检测** | 同类任务中历时异常长的，提示可能被搁置 |

**不能做的：当作估时的标签（label）。**

```
日历时间 = 净投入 + 等待 + 搁置
```

三者比例**因任务而异** —— "等评审意见"和"自己写代码"在日历上长得一样，一个是纯等待、一个是纯投入。
用日历时间去学，会得到"写论文需要 3 周"这类结论，而这个数字里绝大部分不是你的时间。

**被忽略的、更好的信号：推进次数 `len(nodes)`。**

跨度受搁置影响极大（30 天里可能只有 3 天在动），而每次推进至少意味着一次上下文重建，
所以推进次数比跨度更接近真实投入。两个跨度相同、一个推进 10 次、一个推进 2 次的任务，
前者投入大概率更多。

分工：**做相对比较用推进次数，做上界约束用跨度。**
（前提是节点记录习惯相对稳定，记录稀疏时该信号会失真。）

**定位总结：日历时间是阶段 3 的特征，不是阶段 0 的标签。**

#### 2.8.3 "记忆"的实现

不需要向量库或 embedding。所需的东西在数据结构上极简：

| 组成 | 存放 | 说明 |
|------|------|------|
| 历史配对 `(estimate_h, actual_h)` | 直接放在 `task_flows.json` 的任务对象上 | 不新增文件 —— 它就是任务本身的属性 |
| 校准系数 | 页面实时计算，**不落盘** | 任务量级只有几十条，O(n) 计算，没有缓存的必要 |

即：**估时校准的本质是"一个字段 + 一次均值计算"**，不构成一个需要维护的独立系统。

#### 2.8.4 两种回填的数据成本（重要的区分）

| 目标 | 需要的数据 | 成本 |
|------|-----------|------|
| **估时校准**（本节） | **任务级**的 `(estimate_h, actual_h)` 配对 | **低** —— 任务完成时记一个数 |
| 排程执行率分析（§9.4） | 每日明细（实际用时 + 干扰） | 高 —— 每天都要维护 |

**这个区分带出一个关键的实施结论：估时校准不必等第二期。**

它只需要每个任务在完成时有两个数字，不需要每天维护。因此：

- **`actual_h` 字段与录入入口应当随第一期一起做**（见 §6 第 9 项）
- 理由不是"功能相关"，而是**数据积累有天然的时间下限**：阶段 1 需要约 10 条配对，
  若等到第二期才加录入入口，就等于白等两周 —— 而且届时没有任何东西可算

#### 2.8.5 路线：四步，不要跳

| 阶段 | 做什么 | 前提样本 |
|------|--------|----------|
| 1 | **全局偏差系数**（一个数） | 约 10 条配对 |
| 2 | **分类别偏差系数** | 每个分类约 8 条 |
| 3 | 加入特征拟合（`total_days`、`len(nodes)`） | 阶段 2 不足时 |
| 4 | 语义相似任务匹配 | 阶段 3 不足时（通常不需要） |

**阶段 1 的一个数就能解决约 80% 的问题** —— 因为规划谬误是系统性的、方向一致的。
阶段 2 才开始产生领域洞察（"科研类我总是低估 50%，工程类只低估 20%"）。

**阶段 4 最诱人，也最脆弱**：它要求任务命名规范、粒度一致，否则"类似任务"的匹配全是噪声。
现实中的任务名往往很随意，因此不要一开始就追求它。

#### 2.8.6 落地的交互形式

不是"Agent 给出一个数"，而是：

```
你估 4h
  → 系统提示：按你的历史系数 1.44，实际可能 5.8h
```

三个连带好处：保留情境判断、消除系统偏差，且**你会持续校准自己的直觉** ——
每次都看到修正结果，慢慢就不再低估了。

#### 2.8.7 一个提醒

不要过早把估时整个外包出去。**估时的过程本身就是"想清楚要做什么"的过程** ——
要动手拆解任务、想象执行路径、识别依赖，这个价值往往比那个数字更大。
Agent 修正的是数字，替代不了这个思考。

### 2.9 任务后评估

#### 2.9.1 定位：分层，而不是"人填还是程序算"

后评估发生在任务刚结束时 —— 那一刻正想赶紧开始下一件事，情绪上是"这事终于完了"，最不想回顾。
所以真正的问题不是"要不要人填"，而是**能否让人填的成本低到可以接受**。

| 层 | 内容 | 谁来做 |
|----|------|--------|
| **事实层** | 完成时间、总历时、估时偏差、节点节奏、最长空档、停滞区间、延期天数 | **Python 全自动** |
| **归因层** | 卡在哪、为什么卡、下次怎么避免 | **人**，但以选择为主 |

两端的失败模式都很清楚：纯自动只能说出"停滞了 12 天"，永远说不出"因为等合作者回邮件"；
纯人工则退化成开卷作文，写两次就没人再写。

#### 2.9.2 事实层（全部自动，零填写成本）

| 指标 | 来源 |
|------|------|
| 完成日期、总历时 | `completed_date` / `total_days`（已有派生） |
| 计划周期与延期天数 | `start` / `due` / `delayed`（已有派生） |
| 估时与实际 | `estimate_h` / `actual_h`（§2.8.4） |
| 各阶段耗时 | `nodes[].days_from_prev`（已有派生） |
| 最长空档 / 停滞区间 | 由节点日期序列求得 |
| 推进次数与节奏 | `len(nodes)` / 节点密度 |
| 象限归属 | `quadrant` |

**这一层不做任何询问，全部由生成器算好。**

#### 2.9.3 归因层：定向提问，而不是空表

**核心做法：先自动填满事实层，再只针对异常提问。** 两种问法的差距：

| 问法 | 体验 |
|------|------|
| `卡点：______` | 开卷作文，无从下笔 |
| `检测到 8/20–9/1 有 12 天无推进，当时卡在哪？` + 预填选项 | 有锚点、可点选，几秒完成 |

**带日期与数字的锚点让回忆有抓手，预填选项让填写从"写"变成"点"。**
这是决定后评估会不会被持续使用的关键。

自动触发的提问类型：

| 检测到 | 提问 |
|--------|------|
| 停滞区间 > 5 天 | 这段时间卡在哪？（选卡点类型） |
| `actual_h / estimate_h` > 1.5 | 低估的主要原因？（需求不清 / 依赖他人 / 返工 / 想当然） |
| `delayed` 为真 | 延期原因？ |
| 同类任务耗时差异 > 2 倍 | 这次与上次的差别在哪？ |

**允许跳过。** 不允许跳过的表单一定会被绕过。

#### 2.9.4 卡点必须归类成枚举

自由文本既不能统计也不能复用。卡点类型定义在 `meta.py`（遵守单一来源约定）：

```python
BLOCKER_ORDER = ["需求不清", "依赖他人", "技术难点", "返工", "被打断", "精力不足", "外部阻塞", "估算失误"]

BLOCKER_META = {
    "需求不清": {"color": "#d29922", "hint": "目标或验收标准一开始就不明确"},
    "依赖他人": {"color": "#3b6fb0", "hint": "等回复、等评审、等他人产出"},
    "技术难点": {"color": "#7c6bc4", "hint": "确实需要攻关"},
    "返工":     {"color": "#d6453d", "hint": "做完了才发现方向错"},
    "被打断":   {"color": "#d29922", "hint": "突发事项 / 会议 / 他人请求"},
    "精力不足": {"color": "#5a6577", "hint": "状态差、拖延"},
    "外部阻塞": {"color": "#8893a7", "hint": "设备、数据、权限等"},
    "估算失误": {"color": "#2e9e5b", "hint": "任务本身没问题，是估时偏了"},
}
```

存储格式（任务对象上的数组，卡点带时段，便于与推进时间轴对齐）：

```json
"blockers": [
  { "type": "依赖他人", "from": "2026/08/20", "to": "2026/08/26", "note": "等合作者评审" }
]
```

**归类是让后评估从"回顾"变成"反馈"的前提。** 积累十几条后就能回答：

> 我的任务最常因为什么卡住？

而答案能直接反哺前面的设计：

| 卡点占比最高 | 应该调整 |
|--------------|----------|
| 被打断 | 机动时间（`DAY_BUFFER_H`）不够 |
| 依赖他人 | B 类任务要更早发起协作，不能拖到临近 |
| 返工 | 估时偏差系数上调；任务拆分要更细 |
| 估算失误 | 直接进估时校准（§2.8） |
| 精力不足 | 排程的块结构（§9.5(6)）需要调整 |

#### 2.9.5 记录时机：过程中优于事后

`nodes[].note` 字段已经存在，推进时顺手记一句即可。

**卡点记录的最佳位置是过程的当下，而不是事后的回忆。** 若过程中记了，后评估几乎不用再填
（Python 直接把 note 汇总成时间线）；若没记，后评估就得从记忆里重建，成本高且容易失真。

结论：**后评估页应当反向引导"过程记录"这件事**（在推进表单里提示一句），而不是只依赖完成那一下。

#### 2.9.6 页面结构

```
┌────────────────────────────────────────────────┐
│ No.37 BGP-LS-SPF优化写一个论文        [A] ✏️    │
├────────────────────────────────────────────────┤
│ 完成 2026/09/16 · 历时 15 天（计划 10 天）      │
│ 估时 8h → 实际 11.5h（×1.44）                  │
│ 推进 6 次 · 最长空档 6 天（8/20–8/26）          │
├────────────────────────────────────────────────┤
│ 推进时间轴                                      │
│  8/01 ●──●─●───[ 空档 6 天 ]───●──● 9/16        │
├────────────────────────────────────────────────┤
│ 卡点（1 项）                                    │
│  依赖他人 · 8/20–8/26 · 等合作者评审            │
├────────────────────────────────────────────────┤
│ 检测到 2 处异常，需要确认：                     │
│  ⚠ 实际是估算的 1.44 倍 —— 低估的主要原因？     │
│    [需求不清] [依赖他人] [返工] [想当然]        │
│  ⚠ 有 6 天无推进 —— 当时卡在哪？                │

└────────────────────────────────────────────────┘
```

**推进时间轴**是零填写成本、信息密度最高的一块：横轴日期、节点作刻度、空档用灰条标出，
"哪里卡住了"一眼可见，比一堆数字直观得多。

实现形式上，它既可以作为象限页 / 任务清单页上的**弹窗**，也可以是独立页面
（`output/tasks/review.html`）—— 待实施时再定，不影响上面的数据结构设计。

#### 2.9.7 与估时校准、第二期的关系

后评估不是一个孤立功能，它同时承担三个上游角色：

| 角色 | 说明 |
|------|------|
| **估时校准的数据生产** | `actual_h` 与卡点类型就是 §2.8 的全部输入 |
| **卡点统计的来源** | 累积后产出"最常因为什么卡住"（§2.9.4） |
| 排程配额的校准依据 | `被打断` 占比高 → 调整 `DAY_BUFFER_H`（§1.3） |

**归属：第一期。** 数据依赖已经满足（`nodes` 已有，`actual_h` 按 §2.8.4 本就随第一期做），
且它产出的正是第二期的输入 —— 若放第二期会把顺序颠倒：
**校准算法要等数据，而数据要靠后评估生产。**

## 3. 时间投入比例算法

### 3.1 目标区间

目标区间定义在 `meta.py`（遵守枚举单一来源约定），并注入前端：

```python
QUADRANT_ORDER = ["A", "B", "C", "D"]

QUADRANT_META = {
    "A": {"label": "重要且紧迫",  "action": "马上做", "color": "#d6453d", "bg": "#fdeceb", "min": 20, "max": 25},
    "B": {"label": "重要不紧迫",  "action": "计划做", "color": "#3b6fb0", "bg": "#e8eef8", "min": 65, "max": 80},
    "C": {"label": "紧迫不重要",  "action": "快速做", "color": "#d29922", "bg": "#fef8e8", "min": 0,  "max": 15},
    "D": {"label": "不重要不紧迫", "action": "不做",   "color": "#8893a7", "bg": "#f0f2f5", "min": 0,  "max": 0},
}
```

配色复用现有语义色（红=危险、蓝=主色、琥珀=注意、灰=忽略），与全站视觉语言一致。

### 3.2 区间本身的数学张力（必须先说清楚）

给定：A 20–25%、B 65–80%、C 15%。那么：

```
下界之和：20 + 65 + 15 = 100%   ← 精确成立
上界之和：25 + 80 + 15 = 120%   ← 不可能同时达到
```

**结论：三个象限的上界不能同时取到。** 各象限的区间应理解为"各自的容忍带"，
而不是一组必须同时满足的约束。由此得到两条判定约定：

1. **下界是达标线**：`下界之和 = 100%` 是一个精确可行解（A 20% / B 65% / C 15%），
   因此页面把"三个象限都达到各自下界"作为**合格基准**
2. **上界是警戒线**：某象限超过上界即报警，但页面**不做"总和必须 ≤ 100%"的全局校验** ——
   超限本身就是需要被看见的信号，不该被归一化抹平

页面展示占比时直接给**原始比例**（该象限预估工时 / 已估算总工时），不做归一化、不做加权修正。

### 3.3 实际占比计算

```
实际占比(q) = Σ estimate_h(任务 ∈ q) / Σ estimate_h(全部已估算任务) × 100%
```

**口径说明（重要）**：这个占比衡量的是**任务池的工作量结构**，不是某一周的实际投入结构。
二者类似"库存结构"与"流量结构" —— 本周可以硬按 65% 投 B 类，但只要任务池里 B 类只占 40%，
长期投入迟早被池子拖回 40%。所以**任务池结构是前置指标**：池子偏了，投入一定会偏。

代价是它无法直接回答"这周该投多少小时" —— 那个问题由 §1.2 的"每天目标"列回答（目标区间 × 7h 预算）。
页面同时展示两者，并在底部标注口径，避免把"池子结构"误读成"本周投入"。

三条必须遵守的展示约定：

| 约定 | 原因 |
|------|------|
| 分母**只包含已填 `estimate_h` 的任务** | 未估算任务混进分母会凭空拉低所有象限的占比 |
| 明确标注"基于 n / m 个已估算任务" | 让"数据不完整"可见，而不是给出一个看起来精确的错误数字 |
| 未估算任务打"未估算"角标，**不按 0 计入** | 按 0 计入等价于宣称"这个任务不需要时间"（见 §7.3） |

若全部任务都未估算，占比区显示引导文案（"请先为任务填写预估工时"），而不是显示 0%。

### 3.4 偏差解读（页面的灵魂）

单纯的数字对比没有价值，**偏离方向本身就是诊断结论**：

| 现象 | 诊断 | 建议动作 |
|------|------|----------|
| A > 25% | 救火占比过高，B 类（长期价值）被挤占 | 检查 A 类里有多少其实是"拖成的 A" —— 本可以属于 B |
| B < 65% | **最危险的信号**：长期价值投入不足 | 优先从 C 类回收时间，而不是继续压缩 A |
| C > 15% | 被别人的紧急事项牵着走 | 能委托就委托，能拒就拒 |
| D > 0 | 这些任务可能已经不值得占位 | 确认一下是否真的还要做，不值得就从清单删掉 |
| 未估算任务占比 > 30% | 比例结论不可信 | 补全 `estimate_h` 后再看结论 |

页面在每个象限下方给出对应的一句诊断文案，命中才显示，不刷屏。

## 7. 已知坑与约定

### 7.1 页面返回链接不要硬编码公网域名

`task_flow.html` 的返回链接写死成 `https://www.jevylee.com/tasks_view.html`（`generate_task_flow.py` L387），
本地 `file://` 打开时会莫名跳到线上。新页面一律用**相对路径**（`tasks_view.html`）。

### 7.2 比例类指标必须暴露口径

占比、平均值这类指标，只要分母有筛除条件，就必须把 "n / m" 写在旁边。
一个看起来精确的 62%，比一个诚实标注的"基于 12/43 个任务"危害大得多。

### 7.3 未估算 ≠ 0

按 0 计入等价于宣称"这个任务不花时间"，会让所有象限的占比系统性偏低，且偏差方向一致（无法通过直觉发现）。
未估算任务只参与任务计数，不参与占比计算。

### 7.4 沿用既有约定

- 枚举只改 `meta.py`，页面用 `meta.js()` 注入常量、Python 循环生成 `<option>`
- 不用原生 `alert()` / `confirm()`，用页面内的 `toast()` / `confirmBox()`
- Python 模板里的 JS 不要用反斜杠转义（`\n`、`\d` 会被 Python 吃掉）
- `parse_date()` 保持容错，脏日期不能让 `/api/tasks` 挂掉

### 7.5 不要把机动时间算进分母

比例的分母固定为**净可安排时间**（7h/天），机动预留（1h/天）在分母之外。
用 8h 做分母看着"更完整"，实际是把所有目标小时数摊薄 12.5%：
"A 类每天 1.4–1.75h"会变成"1.6–2h"。A 类本身的量级只有 1 小时多，这个误差足以让结论反转。

## 8. 后续扩展（不在本次范围）

- **象限漂移统计**：记录 `quadrant` 的变更历史，统计"多少任务从 B 漂移到了 A"。
  这是四象限法最有价值的长期指标 —— **漂移率高说明计划环节失效**，比单期占比更能说明问题
- **C 类委托标记**：新增 `delegate` 字段，区分"自己快速做"与"应该交给别人"。判定依据见 §2.5 的 Q5–Q7
- **趋势记录**：把每周的实际占比落盘，看长期走势而非单期快照
- **机动时间消耗记录**：记录每天那 1h 是否被用掉、用在什么上。**长期用满 = 突发常态化**（A 类已失控）；
  **从未动用 = 预留过多**（可考虑并回 B 类）。这是唯一能验证"1h 预留"这个数字是否合理的数据
- **本周计划口径**：给任务加 `this_week` 标记，把占比口径从"任务池结构"切到"本周计划投入"，
  让占比与周预算直接对应（见 §3.3 的口径说明）

## 9. 每日排程（第二期 · 独立功能）

### 9.1 定位：与四象限的关系

四象限解决"分类"，排程解决"决策"。前者是后者的输入，**但两者不是同一个功能**：

| | 四象限（第一期） | 每日排程（第二期） |
|---|---|---|
| 回答的问题 | 我的时间结构对不对？ | 今天具体做什么？ |
| 时间尺度 | 长期结构（周 / 月） | 单日 |
| 算法本质 | 占比统计 + 区间比对 | 硬约束下的装箱 + 优先级排序 |
| 产出 | 一个诊断结论 | 一份可执行清单 |

**两套算法没有可复用的部分**：占比统计的复杂度来自数据完整性（分母口径），
排程的复杂度来自组合选择与优先级冲突，二者的失败模式也不同。
因此第二期单独成模块，**不复用 §3 的计算代码**。

### 9.2 分工：算法定配额，LLM 在配额内选任务

**绝不让 LLM 做算术。** 它会给出总时长 9.5h、比例漂移的安排。正确分工：

| 层 | 承担者 | 内容 |
|----|--------|------|
| 硬约束层 | 确定性算法 | 今日总时长 7h、各象限小时配额、停滞任务必须被捞起、`chunk_h` 粒度 |
| 语义层 | LLM | 在配额内挑具体任务、按依赖与精力排顺序、写一句安排理由 |

配额算好交给 LLM 填空，产出必然合法。

### 9.3 最大的坑：B 类会被"优化"掉

**任何以紧迫度为优化目标的算法，都会把 B 类权重压到最低** —— 因为 B 类不紧迫。
让 LLM 自由发挥，结果会和人的直觉完全一致：整天在灭火，B 类永远排不上。

所以 **B 类配额必须是算法强制的硬约束，不参与"优化"**。这是第二期最重要的一条约束，
也是 AI 排程优于人工排程的唯一真正理由：人有"当下偏好"（本能地挑反馈快的活干，而 B 类反馈周期长），
算法没有这个偏好。

### 9.4 必须闭环：排程 + 回填

只排程不回填，三天后会退化成"每天生成一份没人看的文案"。每日两个动作：

1. 执行后勾选完成 / 记录实际用时
2. 记一句干扰（机动时间被什么占用了）

回填数据是验证下列假设的**唯一**依据：`DAY_BUFFER_H = 1` 够不够、`chunk_h` 粒度合不合理、
配额是否需要按实际执行率调整。

注意区分：这里需要的是**每日明细**（重），而估时校准（§2.8）只需要**任务级配对**（轻）——
两者的数据成本差一个数量级，不要因为前者没做而阻塞后者。

**执行率是第二期的核心健康指标**：低于 50% 说明粒度或配额脱离现实，此时做自动化毫无意义。

### 9.5 算法

**(1) 配额计算（确定性）** —— 按 §3.2 的基准点（下界之和 = 100%）折算到当日预算：

| 象限 | 今日配额 | 允许上浮至 |
|------|----------|-----------|
| A | 7 × 20% = 1.40h | 1.75h（25%） |
| B | 7 × 65% = 4.55h | 5.60h（80%） |
| C | 7 × 15% = 1.05h | —（15% 已是上限） |
| D | 0h | — |
| 机动 | 1h | 独立，不参与分配 |

**(2) 候选选择**

| 象限 | 排序规则 | 理由 |
|------|----------|------|
| A | `delayed` → `days_left` 升序 | 已延期的先救 |
| C | 仅收"必须今天做"的，封顶 1.05h | 超出即拒绝，不做超配 |
| B | **最久未推进优先（LRU）** | B 类都重要，差异只在"多久没碰" |

B 类用 LRU 而不是重要性排序是关键：B 类任务彼此的重要性接近，真正的风险是**被无限期搁置**。
数据现成 —— `nodes` 里最后一次推进的日期可直接算出。

**(3) 顺延规则**

| 情况 | 处理 |
|------|------|
| A 类未完成 | 照常顺延（仍然紧迫） |
| B 类未完成 | 顺延但排到队尾，避免堆积在同一任务上 |
| C 类未完成 | **不自动顺延**，重新判断是否真的"必须今天做" |

**(4) 输出** —— 除"今日做 X"外，必须同时输出**"今日明确不碰 Y"**：划掉一批任务本身就能减负，
这是四象限法在心理层面的作用，不是附赠功能。

**(5) 校验层（不可省略）** —— LLM 填充后必须过一遍确定性校验，不通过则**拒绝回写并返回原因**：

- 总时长 ≤ 7h（机动时间不计入）
- 各象限时长落在配额区间内
- 每个 slot 的时长不超过 `chunk_h`，或为其整数倍
- 任务编号存在于任务池

校验层是"配额锁死"这句话的兑现方式 —— 没有它，§9.2 的分工只是一句口号。

### 9.6 新增数据

| 新增 | 说明 |
|------|------|
| `chunk_h` 字段 | **单次投入粒度**（小时），**上限 2h**（伊利赫定律，见 §1.6）。不解决这个，LLM 会把 12h 的论文任务拆成 6 个 2h 碎片。写论文需要 2h 起步（上下文切换成本高），回邮件可以 0.5h |
| `data/plan_draft.json` | 算法产出的"配额 + 候选池 + 历史提示"，即交给 LLM 的输入 |
| `data/daily_plan.json` | 定稿的当日安排：`slots[{no, hours, order, why}]` + `review{实际用时, 干扰}` |

### 9.7 落地路径

| 路径 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **路径 1（先用）** | 程序产出草案 → AI 读文件生成排程写回 → 页面渲染 | 零 API 依赖，当天可用 | 每天需手动触发一次 |
| 路径 2 | 程序内直连 LLM API，挂进 `run_daily.py` 自动生成 | 无人值守 | 需要 API key 与成本管理 |

**建议先走路径 1**，理由不是"简单"，而是它同时是路径 2 的数据验证：
先确认 AI 的安排实际能被执行多少，再决定要不要自动化。执行率低时，自动化只会更快地产生无人看的文案。

### 9.8 前置条件

第二期开工前必须满足：

- 第一期已跑满 **两周以上**，且 `estimate_h` 覆盖率 > 70%（否则配额没有可靠分母，见 §7.3）
- 已积累至少 10 天的**每日**回填数据（用于校准配额与 `chunk_h`）

注意：估时校准（§2.8）只需要**任务级**的配对数据，与上面的"每日回填"是两回事 ——
后者才是排程执行率分析所必需的，两者不要混为一谈、互相阻塞。

未满足时，第二期产出的排程与随机排布没有本质区别。
